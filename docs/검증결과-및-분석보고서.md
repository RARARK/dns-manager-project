## 1. DNS Resolution — A / CNAME / Wildcard

### 검증 방법
`dnsutils` 컨테이너에서 CoreDNS(172.30.0.10)에 직접 `dig` 질의한다. 호스트 리졸버나 캐시를 거치지 않아 CoreDNS의 응답 자체를 관찰할 수 있다.

### 결과

| 질의 | 응답 |
|---|---|
| `api.lab.test` A (동일 도메인 다중 A) | NOERROR, A 3건 |
| `www.lab.test` CNAME | NOERROR |
| `www.lab.test` A (CNAME 체인) | NOERROR, CNAME → A 3건까지 해석 |
| `alpha.dev.lab.test`, `beta.dev.lab.test` A (Wildcard A) | NOERROR, 둘 다 `10.0.0.99` |
| `anything.cdn.lab.test` A (Wildcard CNAME) | NOERROR, CNAME → `api.lab.test` → A 3건 |
| `nothing.lab.test` A | **NXDOMAIN** |

### 분석
와일드카드는 `*.dev.lab.test`처럼 별표를 포함한 이름 자체가 아니라 **등록하지 않은 임의의 하위 이름**으로 질의해야 의미가 있다. 별표 이름으로 질의하면 CoreDNS가 리터럴 이름으로 매칭해 버려 와일드카드 동작을 검증한 것이 되지 않는다. 본 검증에서는 매 실행마다 임의의 하위 이름을 사용했다.

CNAME 체인 해석은 CoreDNS가 응답에 CNAME 레코드와 최종 A 레코드를 함께 담아 반환한다. 와일드카드 CNAME도 동일하게 동작하여 `*.cdn.lab.test` 하나로 임의의 CDN 하위 도메인을 전부 `api.lab.test`로 보낼 수 있다.

## 2. DNS Forwarding — 내부 도메인 vs 외부 도메인

### 검증 방법
동일한 CoreDNS에 내부 도메인과 외부 도메인을 각각 질의하고 **응답 플래그**를 비교한다. 플래그는 "누가 그 응답에 권한을 갖는가"를 드러내므로, 단순히 "둘 다 응답이 온다"보다 처리 경로를 명확히 구분한다.

### 결과

| 질의 | 플래그 | 해석 |
|---|---|---|
| `api.lab.test` (내부) | `qr aa rd` | **aa = authoritative.** CoreDNS가 로컬 존의 권한 서버로서 직접 응답 |
| `google.com` (외부) | `qr rd ra` | **aa 없음, ra = recursion available.** upstream에 전달 후 중계 |

추가로, 관리하지 않는 내부 존 이름(`unknown.lab.test`)은 외부로 나가지 않고 NXDOMAIN으로 응답한다. 로컬 존에 대한 권한이 CoreDNS에 있으므로 "모르는 이름"이 아니라 "없는 이름"으로 처리되는 것이며, 이것이 내부 영역이 제대로 분리되어 있다는 증거다.

### upstream 변경의 동적 반영
UI(또는 `PUT /forwarding`)에서 upstream을 도달 불가 주소(`192.0.2.1`, RFC 5737 TEST-NET)로 바꾸면:

- 외부 도메인 → `;; no servers could be reached`
- 내부 도메인 → **NOERROR (영향 없음)**

정상 주소로 되돌리면 즉시 복구된다. 백엔드가 Corefile을 다시 생성하고 CoreDNS의 `reload` 플러그인이 변경을 감지해 스스로 설정을 재적재하므로 **컨테이너 재시작이 필요 없다.**

## 3. Dynamic DNS Update — UI 변경의 실제 반영

### 결과

| 단계 | DNS 응답 |
|---|---|
| 변경 전 | NXDOMAIN |
| 등록 (`10.0.0.111`) | NOERROR, `10.0.0.111` |
| 수정 (`→ 10.0.0.222`) | `10.0.0.222` |
| 비활성화 | NXDOMAIN |
| 삭제 | NXDOMAIN |

모든 변경은 감사 로그(`/audit-logs`)에 시각과 함께 기록된다.

### 반영 지연 측정

저장 요청 시작 → 저장 응답 수신 → DNS에서 새 값이 처음 관측된 시점을 각각 측정했다(실험 `3-9`, 5회).
밀리초 단위 측정이 필요해 `dig` 컨테이너(기동만 수 초) 대신 백엔드 컨테이너에서 CoreDNS에 직접 질의한다.

| 회차 | 저장 응답(ms) | 응답 → DNS 반영(ms) |
|---|---|---|
| 1 | 8.8 | 1,850.5 |
| 2 | 10.5 | 1,989.8 |
| 3 | 14.1 | 1,988.7 |
| 4 | 13.4 | 1,984.3 |
| 5 | 15.5 | 1,980.1 |
| **평균** | **12.5** | **1,958.7** |

순수 DNS 질의 1회 왕복: **0.92 ms**

### 분석 — 세 가지 시점을 구분해야 한다

이 수치의 핵심은 **저장과 반영이 다른 시점**이라는 점이다.

1. **저장(약 12 ms)** — DB 커밋과 존 파일 기록이 끝난 시점
2. **반영(약 2초)** — CoreDNS가 존 파일을 다시 읽은 시점. `file` 플러그인의 `reload 2s` 폴링 주기가 그대로 나타난다
3. **클라이언트 캐시(TTL 30초)** — 위 둘과 무관한 별개의 축. 이미 응답을 받아 캐싱한 클라이언트는 TTL이 만료될 때까지 옛 값을 쓴다

측정값 평균 1,959 ms는 폴링 주기 2초와 일치하므로, 지연의 원인이 DB나 파일 I/O가 아니라 **CoreDNS의 감지 주기**임이 확인된다. 순수 질의 왕복이 0.92 ms인 것도 이를 뒷받침한다. 반영을 더 빠르게 하려면 폴링 주기를 줄이면 되지만, 그만큼 CoreDNS가 파일을 다시 파싱하는 빈도가 올라간다.

이 "저장은 됐지만 아직 반영 전"인 구간이 UI에서 보이지 않으면 사용자는 시스템이 고장 났다고 오해한다. 그래서 존 파일의 SOA serial과 CoreDNS가 실제로 응답하는 SOA serial을 비교하는 `GET /sync-status`를 만들고, UI 헤더에 상태 배지를 두었다.

| 배지 | 조건 |
|---|---|
| `DNS 반영됨` | 두 serial 일치 |
| `DNS 반영 중 0.1s` | 존 파일이 앞서 있음 (경과 시간 표시) |
| `DNS 응답 없음` | CoreDNS에 질의 불가 |

저장 토스트도 `DNS 반영 중...` → `DNS 반영 완료 — 0.5초 만에 반영됨`으로 바뀐다. (증빙: `docs/screenshots/05`, `06`)

## 4. Service Discovery — 하나의 도메인, 여러 API 서버

### 검증 방법
`api.lab.test` 하나에 세 노드의 A 레코드를 등록하고, **IP가 아닌 도메인으로** HTTP 호출한다. 컨테이너의 resolver를 CoreDNS로 지정해 실제 디스커버리 경로를 탄다.

### 결과

응답 순서가 질의마다 회전한다(`loadbalance round_robin`):

```
[1] 172.30.0.21 172.30.0.23 172.30.0.22
[2] 172.30.0.22 172.30.0.23 172.30.0.21
[3] 172.30.0.23 172.30.0.21 172.30.0.22
[4] 172.30.0.21 172.30.0.22 172.30.0.23
[5] 172.30.0.22 172.30.0.21 172.30.0.23
```

도메인으로 30회 호출한 분포:

| node1 | node2 | node3 |
|---|---|---|
| 13 | 9 | 8 |

CNAME(`www.lab.test`)을 통한 접근도 정상 동작한다.

### 분석 — 이것은 로드밸런서가 아니다
분산의 주체는 서버가 아니라 **클라이언트**다. CoreDNS는 응답에 담긴 A 레코드의 **순서만** 섞고, 실제로 어느 노드에 접속할지는 클라이언트가 고른다. 따라서

- 분포가 정확히 1/3씩 균등하지 않다 (위 결과도 13/9/8)
- 응답을 캐싱하는 클라이언트는 TTL 동안 같은 노드에 고정된다
- 죽은 노드를 DNS는 알지 못한다 — 이것이 5장의 전제가 된다

## 5. Failure Handling — 장애 대응 분석

### 검증 설계
단순히 "노드를 끄고 복구한다"로는 장애의 영향을 수치화할 수 없다. 클라이언트가 DNS 응답을 어떻게 쓰느냐에 따라 체감이 전혀 다르기 때문이다. 두 가지 클라이언트 모델을 함께 측정했다.

- **모델 A (단순 클라이언트)** — DNS 응답의 첫 주소만 사용. 브라우저나 일반 HTTP 라이브러리의 기본 동작에 가깝다
- **모델 B (curl 기본)** — 첫 주소 실패 시 다음 주소로 폴백. 성공하지만 지연이 발생한다

### 결과 — 모델 A (30회 호출)

| 상태 | node1 | node2 | node3 | 실패 | 실패율 |
|---|---|---|---|---|---|
| 정상 | 13 | 9 | 8 | 0 | 0% |
| node1 중지, **DNS 미조치** | — | 8 | 9 | **13** | **43%** |
| node1의 A 레코드 **비활성화 후** | — | 13 | 17 | **0** | **0%** |
| node1 재기동 + 레코드 재활성화 | 7 | 14 | 9 | 0 | 0% |

### 결과 — 모델 B (응답 시간)

20회 중 발췌:

```
[ 5] node3 | 0.002361s
[ 6] node2 | 2.503912s   ← 죽은 노드를 먼저 시도, TCP 타임아웃 후 폴백
[ 7] node2 | 0.557586s   ← 폴백 (더 짧은 경로)
[ 8] node2 | 2.503956s
[ 9] node2 | 0.560294s
[10] node2 | 2.503424s
[11] node2 | 0.002509s
```

20회 중 **2.5초대 폴백 5건, 0.55초대 폴백 4건** — 절반 가까이가 지연을 겪었다.
레코드 비활성화 후에는 20회 전부 정상이며 **최대 지연이 0.006초**였다.

### 분석

**① DNS는 장애를 스스로 알지 못한다.** 노드를 중지해도 A 레코드는 그대로 남아, DNS는 죽은 주소를 계속 응답한다. 모델 A의 실패율 43%(30회 중 13건)는 이를 직접 보여준다(이론값 1/3, 분포 편차로 43%).

**② 장애의 비용은 클라이언트 모델에 따라 형태가 다르다.** 같은 장애에서 모델 A는 **실패**로, 모델 B는 **지연**으로 나타난다. 모델 B는 겉으로는 전부 성공하지만 응답 시간이 0.002초에서 **2.504초로 약 1,250배** 늘어난다. 이 값이 2.5초 부근에 몰리는 것은 TCP 연결 타임아웃이 끝나야 다음 주소를 시도하기 때문이다. "실패율 0%"만 보고 정상이라 판단하면 실제 사용자 경험의 악화를 놓친다.

**③ DNS 레코드 조작은 유효한 장애 대응 수단이다.** 죽은 노드의 A 레코드를 비활성화하자 모델 A의 실패율이 **43% → 0%**, 모델 B의 최대 지연이 **0.006초**로 돌아왔다. 애플리케이션을 전혀 건드리지 않고 이름 해석 계층만 바꿔 서비스 접근을 복구한 것이다.

**④ 다만 즉시 복구는 아니다.** 레코드 비활성화가 DNS에 반영되기까지 CoreDNS 폴링 주기(약 2초)가 필요하고, 그 뒤에도 이미 캐싱한 클라이언트는 TTL(30초)이 만료되어야 새 응답을 받는다. 즉 **TTL은 장애 대응 속도의 상한**이다. TTL을 길게 잡으면 평상시 질의 부하는 줄지만 장애 대응이 그만큼 늦어진다 — 본 시스템이 TTL 기본값을 30초로 둔 이유다.

**⑤ 이 대응은 수동이다.** 본 과제는 모니터링을 범위에서 제외하므로 헬스체크 결과로 레코드를 자동 조작하지 않는다. 운영자가 장애를 인지하고 UI에서 비활성화하는 흐름이며, 그 판단 근거가 되는 `/health`·`/info`는 각 노드가 제공한다.

## 6. 예외 상황 및 방어 동작 (추가 검증)

필수 실험 외에, 잘못된 입력이 DNS 서비스를 망가뜨리지 않는지 별도로 검증했다(`06-robustness.sh`).

| 항목 | 결과 |
|---|---|
| A 레코드에 IP가 아닌 값 수정 | `422` 거부, DNS 정상 유지 |
| TTL 범위 밖 (0 / -5 / 999999999) | 전부 `422` |
| CNAME 공존 규칙 위반 (생성 경로) | `409` |
| CNAME 공존 규칙 위반 (비활성→활성 경로) | `409`, **거부 후에도 다른 레코드 추가 `201`** |
| CNAME 자기참조 / 순환 참조 | `409` |
| 같은 1초 안에 3회 연속 변경 | serial 단조 증가, **3건 모두 반영** |
| 멱등성 (POST 4회 / PATCH 3회 / DELETE 3회) | 저장 1건, 감사 로그 증가분 1건, `204` |
| 질의 테스트 비정상 도메인 | `422` |
| forwarding 주입성 입력 (`8.8.8.8; rm -rf /`) | `422`, 기존 설정 보존 |
| **CoreDNS 존 파싱 에러** | **0건** |

잘못된 요청 **13건이 모두 4xx로 거부**되었고, 거부 이후에도 시스템은 계속 정상 동작했다.

## 7. 검증 과정에서 발견한 주요 결함과 분석

기능 테스트만으로는 드러나지 않았던 결함들이다. 본 과제에서 가장 의미 있는 분석 대상이라 판단해 별도로 정리한다.

### 7.1 DNS 변경이 조용히 유실되는 결함

**증상** 같은 실험 스크립트를 두 번 돌렸는데 결과가 달랐다. 한 번은 CNAME과 와일드카드가 정상 응답했고, 다른 한 번은 둘 다 NXDOMAIN이었다.

**원인** 존 파일의 SOA serial을 `int(time.time())`, 즉 **초 단위**로 생성하고 있었다. CoreDNS의 `file` 플러그인은 serial이 직전에 적재한 값과 **같으면 파일 내용이 달라도 재적재를 건너뛰고, 그 사실을 로그로도 남기지 않는다.**

**재현** 폴링 간격보다 길게 띄워 통제 실험한 결과:

| 단계 | 파일 | DNS 응답 |
|---|---|---|
| serial=S + 레코드 `z1` | — | `z1` NOERROR |
| **serial=S 그대로** + `z2`로 교체 | 내용 변경됨 | `z2` **NXDOMAIN**, `z1` 아직 응답 |
| serial=S+1 + `z2` | 동일 내용 | `z2` NOERROR |

초기 레코드 5건을 1초 안에 연속 등록하는 과정에서 CoreDNS의 폴링이 그 사이에 끼면, 뒤에 등록한 레코드가 **영구히 유실**된다. 이후 다른 변경이 발생해 serial이 올라가야 비로소 복구되므로, 증상이 간헐적으로만 나타났다.

**조치** 기존 파일의 serial을 읽어 반드시 그보다 큰 값을 쓰도록 변경했다. 같은 초에 3회 연속 변경 시 serial이 `1795171051 → 1795171052 → 1795171053`으로 증가하고 3건 모두 반영됨을 확인했다(실험 `6-5`).

**분석** 외부 컴포넌트의 "변경 감지 조건"을 잘못 이해한 데서 비롯된 결함이다. 파일을 올바르게 썼는지만 확인하고 상대가 그것을 읽었는지는 확인하지 않았다. 이 경험이 `/sync-status`(존 파일 serial과 CoreDNS 응답 serial 비교)를 도입한 직접적인 계기가 되었다.

### 7.2 한 번의 잘못된 입력으로 DNS가 고착되는 결함

**증상** 수정 API에 IP가 아닌 값을 넣으면 `200 OK`가 반환되었다.

**연쇄** 잘못된 값이 그대로 존 파일에 기록되어 CoreDNS가 파싱에 실패한다. 이때 CoreDNS는 **직전에 적재한 존을 계속 서빙하고 에러는 로그에만 남긴다.** 그 결과 이후 정상 레코드를 추가해도 API는 `201`을 돌려주지만 DNS는 NXDOMAIN을 응답하는, **API는 성공하는데 DNS는 영구히 낡은** 상태가 된다. 증거는 컨테이너 로그에만 있어 UI로는 전혀 보이지 않는다.

**조치** 두 겹으로 막았다.
1. 수정 API에도 타입별 값 검증 추가 (`422`)
2. 존 파일을 **교체하기 전에** 파싱 검증 — 어떤 경로로도 깨진 존이 CoreDNS에 도달하지 못한다

**분석** 단일 검증에 의존하지 않고 "입력 검증"과 "출력 검증"을 분리한 것이 핵심이다. 실제로 이후 발견한 다른 결함(정규식 앵커 문제로 도메인에 개행이 들어가는 경우)도 입력 검증을 통과했지만 존 검증 계층에서 차단되어 존 파일이 손상되지 않았다.

### 7.3 트랜잭션 경계 결함 — 거부가 시스템 전체를 멈춤

**증상** CNAME 충돌이 발생하는 경로에서 `500`이 반환되고, 그 뒤 **무관한 레코드 추가까지 전부 `500`** 이 되었다.

**원인** `db.commit()` **뒤에** 존 파일을 쓰고 있었다. 파일 쓰기가 실패해도 DB는 이미 커밋된 상태라 DB와 DNS가 어긋나고, 이후 모든 요청이 같은 지점에서 다시 실패했다.

**조치** 순서를 **검증 → 쓰기 → 커밋**으로 바꿔 실패 시 롤백되게 하고, 충돌은 `409`와 설명 메시지로 거부하도록 했다. 거부 후에도 다른 레코드 추가가 `201`로 동작함을 확인했다.

### 7.4 재동기화 루프의 경쟁 조건

DB와 파일이 어긋났을 때 수렴시키는 주기적 재동기화 루프를 추가했는데, 이 루프 자체가 결함을 만들었다.

**원인** 파일 쓰기만 락으로 감싸고 커밋은 락 밖에 두어, 그 사이에 루프가 끼어들 수 있었다. 루프는 별도 DB 세션이라 **아직 커밋되지 않은 변경을 보지 못하고**, 방금 쓴 파일을 직전 상태로 되돌렸다.

**재현** 운영 설정에서는 창이 마이크로초 수준이라 200회 시도에 0건이었다. 커밋 전 구간을 120 ms로 인위적으로 넓히자 **200회 중 167회** 재현되었다. 락을 커밋까지 확장한 뒤 동일 조건에서 **0회**가 되었다.

**분석** 재현되지 않는다고 없는 결함이 아니다. 발생 확률이 낮을 뿐 조건이 맞으면 반드시 발생하며, 증상은 "가끔 DNS가 옛 값을 돌려준다"로 나타나 원인 추적이 매우 어렵다. 실패 조건을 의도적으로 확대해 재현한 뒤 수정하고, 같은 조건에서 사라졌음을 확인하는 절차가 필요했다.

### 7.5 환경 의존성 — 내 환경에서만 통과하던 검증

요구사항 대조 검증이 원래 환경에서는 전부 통과했으나, `.gitignore` 대상을 제외해 새 폴더에 복사한 **클린룸 환경에서는 3건이 실패**했다.

| 실패 항목 | 원인 |
|---|---|
| Wildcard CNAME 검증 | 해당 레코드는 실험 1이 만드는 것인데, 검증 스크립트가 "이미 있겠지"라고 가정 |
| 실험 로그 보관 (2건) | `run-all.sh`를 한 번도 돌리지 않은 상태 |

원래 환경에서는 이전 실행의 잔재 덕분에 계속 통과하고 있었다. 검증 스크립트가 필요한 레코드를 직접 만들고 되돌리도록 자립화하고, 선행 조건이 필요한 항목은 `SKIP`으로 구분하도록 수정했다. 수정 후 클린룸에서 **FAIL 0**이 되었다.

**분석** 검증 도구 자체가 환경에 의존하면 검증 결과를 신뢰할 수 없다. "같은 코드를 새 환경에 놓고 문서만 보고 실행한다"는 절차가 아니었다면 끝까지 발견되지 않았을 문제다.

구현 범위 밖으로 두었거나, 확인했으나 해결하지 않은 항목을 기록한다.

| DB·파일 불일치 가능성 | 쓰기 성공 후 커밋 실패 시 어긋날 수 있다. 재동기화 루프가 20초 주기로 수렴시키지만 그 구간은 남는다 |
| 감사 로그 보존 정책 없음 | 계속 쌓이기만 한다. 조회는 기본 200건으로 제한했으나 삭제·아카이브 정책은 없다 |
